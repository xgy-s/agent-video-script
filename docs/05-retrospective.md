# 05 复盘文档 — 最难问题、学习收获、下一步

## 最难的问题：让"真实模型"稳定走完 ReAct 闭环

Mock 一次跑通不等于真实模型可用。真实联调连续踩了三个坑，按难度排序：

1. **qwen 输出截断 JSON（最难）**。`check_rules` 的 script 参数较长时，模型返回的 arguments 尾部缺 `}`，`json.loads` 直接崩溃。最初加的重试无效——temperature=0 下模型确定性复现同样的截断。最终方案是**先修复后重试**：扫描括号栈补全截断 JSON（`_close_truncated_json`），把"模型能力缺陷"降级为"可本地修复的格式问题"。这让自己意识到：Agent 工程里模型输出的健壮性处理和决策逻辑同等重要。
2. **模型对终止动作的滥用**。初版 prompt 只写"缺关键信息时请求补充"，模型就把"品牌规则未提供"也当成缺失信息。教训：prompt 中每个动作的**适用边界必须显式负向约束**（"仅当 topic/duration 缺失时"），否则模型会按字面泛化。
3. **失败信号被正常结果污染**（测试抓出）。Mock 状态解析把 ERROR 消息按"0 命中"处理，工具失败场景静默走错分支。pytest 的 A4 断言直接暴露了它——这是"先写验收测试"价值的实证。

## 学习收获

- **ReAct 的本质是"结束也是动作"**。把 submit/declare_unfinished/report_failure 都建模为 function tool 后，"模型何时结束、以什么状态结束"变成可核对的事件流，评审时逐条 Trace 可追溯，这比在代码里埋 if/else 判断结束条件干净得多。
- **失败要作为观察回传，而不是骨架自动重试**。自动重试会偷走模型的决策权，考核要求的分支也就消失了；骨架只应记账（步数/调用上限）。
- **启发式估算器要写出口径假设**。4.5 字/秒这个数字本身不重要，重要的是它确定、可断言、文档里交代了来源假设。
- **temperature=0 的副作用**：错误会确定性复现。调试时这是优点，但也意味着"重试"不能作为唯一的容错手段。

## 下一步（如有更多时间）

1. **抑制冗余工具调用**：[case8_real_step_limit.json](../examples/case8_real_step_limit.json) 中模型开局连续检索两次相同关键词，浪费一步。可在 prompt 加"同一查询勿重复检索"，或在骨架中对相同参数调用去重（计入 Trace 但不消耗模型步数）。
2. **检索升级为向量召回**（如 bge-small 本地嵌入），当前关键词包含匹配对同义改写（"榨汁"vs"破壁"）无能为力。
3. **时长估算校准**：用真实 TTS 跑一批旁白，拟合实际语速分布，给出误差区间。
4. **失败步骤续跑**：把任务状态持久化，支持从上次失败点恢复（题 2 的加分项思路同样适用于本题）。
5. **夸大表述的语义检测**：正则只能抓数字型结论，"遥遥领先"类无数字表述需要小型分类模型兜底。

## 实际用时

约 2.5 小时（规划与骨架 0.5h、工具与 Mock 0.5h、测试 0.5h、真实模型联调与修复 0.7h、文档 0.3h），在建议的 3 小时预算内。界面、部署、多 Agent 按考核说明未做。
